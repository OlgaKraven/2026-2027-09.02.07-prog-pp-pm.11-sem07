3.1. Основной маршрут

Начало и личный маршрут

  1. 1

    Определить свою работу

    Найти назначенный вариант в списке предметных областей. Прочитать полное общее задание до блока файлов. Создать одну рабочую папку своей области и папку доказательств. Прочитать разбор «Пары», затем выполнить аналогичные действия на собственных данных; обязательное повторное приложение на «Паре» не требуется.

    Проверка. Записаны номер, область и путь рабочей папки; выбраны только условия своего варианта.

  2. 2

    Как пользоваться разбором

    Основной маршрут ниже задаёт порядок выполнения. После каждого этапа указаны разделы подробного справочника с сохранёнными объяснениями и кодом. Сначала выполнять этап маршрута, затем читать относящиеся к нему части справочника. Разделы готовых входа, отбора и цены служат объяснением поставляемых компонентов; переписывать их как новое задание не нужно.

    Проверка. Исходная БД не изменялась; выбранная рабочая копия содержит собственную область.

  2. 2

    Зафиксировать контрольные числа

    В SQL выполнить COUNT(*) для product, size, stock_item, customer, sales_order, order_line; затем SUM(available) из stock_item и SUM(total) из order_totals. 3.7. Основной маршрут

Первый проверочный заказ

  1. 1

    Получить реальные значения

    В phpMyAdmin в административном подключении рабочей копии выполнить код ниже одним сеансом. Выбирается положительный остаток собственной позиции. При отсутствии такой позиции остановиться и проверить исходные данные; не подставлять 1 вслепую. Сохранить item_id, клиента, исходный остаток и количества заказов.

  2. 2

    Получение ID и контроль заказа

    SET @actor=(SELECT customer_id FROM customer WHERE login='pp_client');
SET @item=(SELECT item_id FROM stock_item WHERE available>0 ORDER BY item_id LIMIT 1);
SET @before=(SELECT available FROM stock_item WHERE item_id=@item);
SET @key=UUID();
SELECT @actor AS customer_id,@item AS item_id,@before AS stock_before;
CALL pp_checkout(@actor,@actor,JSON_ARRAY(JSON_OBJECT('item_id',@item,'quantity',1)),@key);
SET @order=(SELECT order_id FROM sales_order WHERE request_key=@key);
SELECT o.order_id,o.customer_id,l.item_id,l.quantity,l.unit_price,l.quantity*l.unit_price AS total
FROM sales_order o JOIN order_line l USING(order_id) WHERE o.order_id=@order;
SELECT @before AS before_value,available AS after_value FROM stock_item WHERE item_id=@item;
  3. 3

    Сравнить результат

    В таблице результата есть один новый заголовок, строка выбранной позиции с quantity=1, сохранённая unit_price и остаток @before−1. Зафиксировать ID заказа для последующего удаления. После перехода на другую вкладку сеансовые @переменные могут потеряться; получить значения заново запросами к БД.

    Проверка. В отчёте сохранены SQL и реальные числа, а не только сообщение интерфейса.

Подробный разбор: справочник 10.

3.11. Основной маршрут

Обязательные испытания

  1. 1

    Начать с одинакового состояния

    Для независимого испытания восстановить отдельную проверочную копию из своего экспорта. Записать начальные количества заголовков, строк и остатки выбранных позиций. Не переносить изменённые остатки одного опыта в следующий без фиксации. Разделить ожидаемое значение, фактическое значение и вывод.

  2. 2

    Успех и отказ

    Оформить две разные размерные позиции; сравнить обе строки и уменьшение каждого остатка. Отменить другую непустую корзину и выйти из карточки без добавления: количества заголовков и строк, остатки прежние. Для отказа запросить у второй позиции остаток+1: новый заголовок и первая строка не сохраняются, оба остатка прежние.

    Проверка. Снимок интерфейса дополнен SELECT до/после; сообщение об ошибке не считается доказательством полного отката.

  3. 3

    Роли и удаление

    Менеджером оформить заказ другому клиенту и проверить customer_id. Отказаться от предупреждения об удалении — данные прежние. Подтвердить удаление — вернулись все количества. Администратором удалить одну из двух строк, затем последнюю; пустой заголовок исчезает. Повторное удаление не возвращает остаток второй раз. Менеджер не меняет дату и не удаляет строку.

Подробный разбор: справочник 47, справочник 48, справочник 50.

3.12. Основной маршрут

Границы каталога и история цены

  1. 1

    Подготовить остатки 3 4 5 6

    В отдельной копии выбрать product_id, сохранить все его stock_item. Поочерёдно установить суммарные остатки 3, 4, 5 и 6, например обнулить остальные размеры и задать нужную величину одной существующей позиции. После каждого изменения обновить каталог. Проверить SUM(available) WHERE product_id=полученный_ID; после опыта восстановить копию.

    Проверка. 3 — подсветка и «мало»; 4 и 5 — без подсветки, «мало»; 6 — без подсветки, «много».

  2. 2

    Проверить готовую цену

    В проверочной копии выбрать модель, сохранить её цену и историю. Для даты 2027-01-15 сравнить pp_price до и после перемещения её единственного декабрьского заказа на 2027-01-01; остальные декабрьские заказы этой модели вынести за период в этой копии. Это проверка вызова готовой функции, не её повторная разработка. После опыта восстановить исходное состояние.

  3. 3

    Сохранить историческую цену

    Оформить заказ, сохранить unit_price и quantity. Изменить product.price в проверочной копии, затем дату заказа администратором; перечитать каталог и состав. Текущая цена может измениться, старая unit_price и quantity×unit_price должны сохраниться.

Цена относительно календарного месяца

  1. 1

    Где и зачем

  2. 2

    -- === Цена относительно календарного месяца
DROP FUNCTION IF EXISTS pp_price;
DELIMITER $$
CREATE FUNCTION pp_price(p_product BIGINT,p_date DATE)
RETURNS DECIMAL(12,2) READS SQL DATA SQL SECURITY DEFINER
BEGIN
 DECLARE v_start DATE;
 DECLARE v_price DECIMAL(12,2);
 SET v_start=DATE_SUB(p_date,INTERVAL DAYOFMONTH(p_date)-1 DAY);
 SELECT p.price * IF(EXISTS(
  SELECT 1 FROM order_line l JOIN stock_item s USING(item_id)
  JOIN sales_order o USING(order_id)
  WHERE s.product_id=p.product_id
   AND o.ordered_at>=DATE_SUB(v_start,INTERVAL 1 MONTH)
   AND o.ordered_at<v_start
 ),1,0.75) INTO v_price FROM product p WHERE p.product_id=p_product;
 RETURN ROUND(v_price,2);
END$$
DELIMITER ;

RETURNS VARCHAR(20) READS SQL DATA SQL SECURITY DEFINER
BEGIN
 DECLARE v_role VARCHAR(20);
 DECLARE v_account VARCHAR(80);
 SELECT CASE r.name WHEN 'Администратор' THEN 'admin'
  WHEN 'Менеджер' THEN 'manager' ELSE 'client' END

    Где и зачем

    Код: 02_checkout.sql

 SET v_role=pp_role(p_actor);

  SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT='ROLE_DENIED';
 END IF;
 IF p_key IS NULL OR p_key NOT REGEXP
  '^[0-9a-fA-F]{8}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-[0-9a-fA-F]{12}$' THEN

  SELECT created_by INTO v_creator FROM sales_order WHERE order_id=v_order;
  IF v_creator<>p_actor THEN
   SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT='ROLE_DENIED';

  SELECT v_order AS created_order;
  LEAVE proc;
 END IF;

  SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT='INVALID_LINES';
 END IF;
 IF JSON_TYPE(p_lines)<>'ARRAY' OR JSON_LENGTH(p_lines)=0 THEN
  SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT='EMPTY_ORDER';
 END IF;
 IF NOT EXISTS(SELECT 1 FROM customer WHERE customer_id=p_customer) THEN
  SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT='UNKNOWN_CUSTOMER';
 END IF;
 DROP TEMPORARY TABLE IF EXISTS pp_request;
 CREATE TEMPORARY TABLE pp_request(item_id BIGINT PRIMARY KEY,
  quantity INT NOT NULL) ENGINE=InnoDB;
 WHILE v_index<JSON_LENGTH(p_lines) DO
  SET v_id_text=JSON_UNQUOTE(JSON_EXTRACT(p_lines,CONCAT('$[',v_index,'].item_id')));

    Где и зачем

  2. 2

    Код: 03_manage.sql

    -- === Отмена заказа с возвратом всех позиций
DROP PROCEDURE IF EXISTS pp_delete_order;
DELIMITER $$
CREATE PROCEDURE pp_delete_order(IN p_actor BIGINT,IN p_order BIGINT)
SQL SECURITY DEFINER
BEGIN
 DECLARE v_id BIGINT;
 DECLARE v_item BIGINT;
 DECLARE v_qty INT;
 DECLARE v_done INT DEFAULT 0;
 DECLARE cur CURSOR FOR SELECT item_id,quantity FROM order_line
  WHERE order_id=p_order ORDER BY item_id;
 DECLARE CONTINUE HANDLER FOR NOT FOUND SET v_done=1;
 DECLARE EXIT HANDLER FOR SQLEXCEPTION BEGIN ROLLBACK; RESIGNAL; END;
 IF pp_role(p_actor) NOT IN ('manager','admin') THEN
  SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT='ROLE_DENIED';
 END IF;
 START TRANSACTION;
 SET v_id=NULL;
 SELECT order_id INTO v_id FROM sales_order WHERE order_id=p_order FOR UPDATE;
 IF v_id IS NULL THEN
  SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT='ORDER_NOT_FOUND';
 END IF;
 SET v_done=0;
 OPEN cur;
 read_loop: LOOP
  FETCH cur INTO v_item,v_qty;
  IF v_done=1 THEN LEAVE read_loop; END IF;
  UPDATE stock_item SET available=available+v_qty WHERE item_id=v_item;
 END LOOP;
 CLOSE cur;
 DELETE FROM sales_order WHERE order_id=p_order;
 COMMIT;
END$$
DELIMITER ;

  1. 1

    Точные действия в phpMyAdmin

    Вернитесь на уровень сервера → Учётные записи пользователей → Добавить учётную запись пользователя. Имя pp11_demo_login, хост localhost (Локальный), пароль задать локально.   2. 2

    Почему четыре подключения

    Пользователь приложения входит по учебному логину. Соединение с MySQL использует отдельную учётную запись и пароль. Разные EXECUTE ограничивают именно возможности подключения: клиенту не разрешена процедура редактирования даты, даже если вызвать её вне окна. Суффиксы имён _client/_manager/_admin дополнительно сопоставляются с ролью actor функцией pp_role.

  3. 3

    Граница учебного входа

    В этом учебном сценарии вход происходит без пароля приложения. Пользователь, знающий другой учебный логин, может выбрать его; локальный desktop-проект содержит параметры всех учебных подключений. Поэтому этот сценарий показывает работу прав СУБД и проверок роли, но не заменяет серверную аутентификацию реальной торговой системы. Пароли подключений не публиковать.

Справочник 27

Локальная конфигурация и параметризованная команда

Готовый компонент. Изучить и проверить интеграцию; создавать повторно не требуется.

  1. 1

    Где и зачем

    Создать или заменить файл с начала: app/Repository.cs. Фрагмент 1 из 4 этого файла. Создать Repository.cs через Добавить → Класс. Settings читается из каталога исполняемого приложения. Query открывает новое соединение выбранной роли; await не блокирует ожиданием серверного ответа интерфейс. AddWithValue передаёт значения отдельно от SQL, поэтому введённая кавычка не превращается в часть команды. DataTable превращает результат CALL в таблицу данных.

  2. 2

    Код: Repository.cs

    using System.Data;
using System.IO;
using System.Text.Json;
using MySqlConnector;
namespace ShopDb;
public sealed class Repository
{
    // === Локальная конфигурация и параметризованная команда
    public Settings Settings { get; }
    public AppUser? User { get; private set; }
    private string Role => User?.Role ?? "login";
    public Repository()
    {
        string path = Path.Combine(AppContext.BaseDirectory, "settings.local.json");
        Settings = JsonSerializer.Deserialize<Settings>(File.ReadAllText(path))
            ?? throw new InvalidOperationException("Не заполнены настройки подключения.");
        foreach (string key in new[] { "login", "client", "manager", "admin" })
        {
            if (!Settings.Connections.ContainsKey(key))
            {
                throw new InvalidOperationException($"В настройках отсутствует подключение {key}.");
            }
        }
    }
    private async Task<DataTable> Query(string sql, params (string Name, object Value)[] values)
    {
        await using var connection = new MySqlConnection(Settings.Connections[Role]);
        await connection.OpenAsync();
        await using var command = new MySqlCommand(sql, connection);
        command.CommandTimeout = 15;
        foreach (var value in values)
        {
            command.Parameters.AddWithValue(value.Name, value.Value);
        }
        await using var reader = await command.ExecuteReaderAsync();
        var table = new DataTable();
        table.Load(reader);
        return table;
    }

        // === Заказ клиента и выбор клиента сотрудником
    private AppUser Actor => User ?? throw new InvalidOperationException("Сначала войдите по логину.");
    private void Staff()
    {
        if (!Actor.IsStaff)
        {
            throw new InvalidOperationException("Список заказов доступен менеджеру и администратору.");
        }
    }
    public async Task<List<Choice>> Customers()
    {
        if (!Actor.IsStaff)
        {
            return new List<Choice> { new(Actor.Id, Actor.Fio) };
        }
        DataTable table = await Query("CALL pp_customers(@actor)", ("@actor", Actor.Id));
        return table.Rows.Cast<DataRow>().Select(row => new Choice(
            Convert.ToInt64(row["customer_id"]), (string)row["fio"])).ToList();
    }
    public async Task<long> Checkout(long customer, IEnumerable<CartLine> lines, string key)
    {
        string json = JsonSerializer.Serialize(lines.Select(line => new
        {
            item_id = line.ItemId,
            quantity = line.Quantity
        }));
        DataTable table = await Query("CALL pp_checkout(@actor,@customer,@lines,@key)",
            ("@actor", Actor.Id), ("@customer", customer), ("@lines", json), ("@key", key));
        return Convert.ToInt64(table.Rows[0]["created_order"]);
    }

    using System.Windows;
using MySqlConnector;
namespace ShopDb;
public static class Ui
{
    // === Понятное сообщение без строки подключения
    public static async Task Run(Window owner, Func<Task> action)
    {
        try
        {
            await action();
        }
        catch (MySqlException error)
        {
            string text = error.Message.Contains("NOT_ENOUGH_STOCK")
                ? "Остаток изменился. Обновите каталог и уменьшите количество в заказе."
                : error.Message.Contains("ROLE_DENIED") || error.Number == 1370
                ? "Действие запрещено для этой роли. Войдите с разрешённым логином."
                : error.Message.Contains("NOT_FOUND")
                ? "Заказ или строка уже удалены. Обновите список заказов."
                : error.Message.Contains("INVALID_DATE")
                ? "Дата не должна находиться в будущем. Выберите корректную дату."
                : error.Number == 1213 || error.Number == 1205
                ? "Данные сейчас изменяет другой пользователь. Повторите операцию с тем же заказом."
                : "Не удалось выполнить операцию с БД. Проверьте запуск MySQL, имя БД и локальные настройки. При неясном результате подтверждения повторите запрос, не изменяя корзину.";
            MessageBox.Show(owner, text, "Ошибка операции", MessageBoxButton.OK, MessageBoxImage.Error);
        }

Проверка календаря, истории и конкуренции

  1. 1

    Контролируемые даты

    В отдельной проверочной копии выбрать модель, сохранить её исходную цену и историю. Для даты расчёта 2027-01-15 создать тестовый заказ этой модели с ordered_at 2026-12-31 и известной строкой: pp_price(product_id,'2027-01-15') даёт базовую цену. Перенести дату на 2027-01-01: теперь прошлый месяц заказа не содержит, цена составляет 75%. Чтобы исходные данные не мешали, другие заказы выбранной модели в декабре на проверочном наборе временно перенести вне интервала; все изменения выполнять внутри BEGIN/ROLLBACK либо в отдельной копии.

  2. 2

    Историческая цена

    Оформить заказ при действующей скидке. Сохранить unit_price. Администратором изменить базовую product.price в проверочной копии, открыть каталог и состав заказа: текущая цена меняется, сохранённая unit_price прежняя. При изменении даты заказа административной функцией unit_price также не меняется. Не переоценивать историю через UPDATE order_line.

  3. 3

    Последняя позиция

    В отдельной копии установите одному item_id available=1 и открыть два независимых подключения клиента. В первом BEGIN; SELECT available FROM stock_item WHERE item_id=... FOR UPDATE; требует административного проверочного подключения, поскольку клиенту прямой SELECT запрещён. Запустить pp_checkout из двух клиентских соединений с разными ключами; снять блокировку COMMIT в первом проверочном соединении. Только один заказ проходит, другой получает NOT_ENOUGH_STOCK; available=0. Вне тестовой копии не менять остатки ради проверки.

  4. 4

    Что доказывает результат

    Сообщение ошибки подтверждает отказ интерфейса, а контрольные SELECT подтверждают отсутствие частичного изменения. Два соединения подтверждают блокировки при конкуренции; последовательные вызовы лишь подтверждают отказ после исчерпания остатка. Зафиксировать оба вида доказательств.

Справочник 50

Проверка менеджера и администратора

  1. 1

    Менеджер

    Войти pp_manager → Заказы. Выбрать заголовок: нижняя таблица показывает модель, производство, размер, количество, цену и сумму. Нажать Добавить заказ — возвращаетесь к каталогу; выбрать клиента в правом списке, добавить модели и подтвердите. Снова открыть Заказы: дата и ФИО совпадают с выбранным клиентом. Изменить дату и Удалить товарную позицию недоступны.

  2. 2

    Удаление целого заказа

    Выбрать новый небольшой заказ, сохранить остатки его позиций. Удалить заказ → Нет: данные прежние. Повторить → Да: заголовок и строки исчезают, количества возвращаются. После Назад перечитан каталог. Повторное удаление того же order_id через разрешённый CALL получает ORDER_NOT_FOUND и не увеличивает остаток снова.

  3. 3

    Администратор

    Войти pp_admin → Заказы. У заказа с двумя позициями удалить одну: вернулся только её остаток, сумма заказа уменьшилась по исторической цене оставшейся. Удалить вторую: пустой заголовок исчез. Для другого тестового заказа изменить дату; исходные цены не меняются. Будущая дата должна отклониться. Выход возвращает гостя.

  4. 4

    Проверка вне окна

    Войти в phpMyAdmin отдельной сессией pp11_demo_client и попробовать CALL pp_change_date с идентификатором администратора: EXECUTE запрещён. Под менеджерским подключением действие также запрещено. Прямые SELECT customer, UPDATE stock_item и DROP TABLE запрещены всем подключениям приложения. Из клиентского подключения передать actor администратора в pp_checkout: pp_role откажет по несоответствию суффикса.

Справочник 51

Резервная копия и передача пользователю

  1. 1

    Экспорт после доработки

    Выбрать только свою рабочую БД → Экспорт → Обычный → SQL. Включите структуру, данные, функции и процедуры; проверить наличие CREATE FUNCTION pp_price и CREATE PROCEDURE pp_checkout в полученном SQL. Экспорт одной БД не включает серверные учётные записи и GRANT. Пароли и настройки приложения хранятся отдельно локально.

  2. 2

    Восстановление

    Создать новую БД pp11_restore_demo или pp11_restore_vNN → Импорт резервной копии. На том же сервере DEFINER исходных объектов существует. Выполнить точечные GRANT из 05_access.sql с именем восстановленной БД. В settings.local.json заменить Database у всех подключений, собрать и запустить приложение. Сравнить количества, суммы и исторические цены до нового заказа; повторить вход, каталог, подтверждение, список и удаление.

  3. 3

    Передача

    В README указать назначение проекта, используемую СУБД и версию приложения, последовательность создания БД/миграций/локальных подключений, способ запуска и восстановления. Объяснить ограничения учебного входа по логину. Подготовить репозиторий проекта без settings.local.json, паролей, личных путей и данных студентов. При сдаче проекта приложите ссылку на его репозиторий.

  4. 4

    Своя область

    Взять тот же номер варианта из учебной практики. Сохранить схему модели/размера/остатка, заменить Company и подключения, использовать её исходную БД. Данные торговой области не заменяются обувным набором демонстрации. Изображения, которых нет, корректно показываются через заглушку. Выполнить оба дополнительных условия области и повторить общие проверки.
